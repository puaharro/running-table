# RMAC 工作流與 CMS 改進評估

評估基於 2026-11-12 本機 RMAC 工作紀錄、CMS 七類來源與網站稿資料、現有程式及已完成的發布流程。這是流程／產品評估，沒有重新搜尋來源、重跑研究或效能量測；優先次序屬建議，未實作。

## 判斷

現有系統已適合單一擁有人逐場研究及審稿：材料可去重及留版、proposal 接受只存草稿、網站確認綁版本與雜湊、依據更新阻擋舊匯出、私人資料不隨靜態網站發布。主要成本在研究結果到 proposal、網站稿、正式頁的交接，需要人手反覆搬運與跨頁確認。

## 今次實際暴露的問題

| 問題 | 實際跡象與影響 | 建議 |
| --- | --- | --- |
| 查過平台與取得可用證據混在一起 | 最後七類紀錄為五類 reviewed、兩類 no_results；YouTube 已讀資料仍只是線索，網誌只是賽前計劃。全部有進度不等於五個主題都有證據 | 分開顯示搜尋覆蓋、原文已讀、可採用證據及主題缺口；不要只顯示「研究完成」 |
| 查閱時間與保存時間界線不清 | 七類 checked_at 相同；不足以由資料庫時間還原各平台實際讀取時刻 | 每次搜尋嘗試獨立記 read_at；自動 saved_at 不代填 read_at；歷史不足不倒填精確時間 |
| 檢索路徑不夠結構化 | 目前每平台一組 query／links／notes，有版本歷史，但多次嘗試、站內排序及搜尋頁多塞在備註；no_results 的原文連結可為空 | 新增 append-only 搜尋嘗試，分開搜尋 URL、原文 URL、篩選、載入範圍及結果 |
| 登入有協作但恢復靠對話 | 今次兩個平台由擁有人完成登入／驗證後才續查 | 保留來源的原分頁、最後查詢及下一動作；「已登入」只進搜尋中，續查後才可結束該輪 |
| 重讀範圍靠長篇文字維護 | 曾出現「部分重讀」與「未重新核對」措辭矛盾 | 每則材料記本輪重讀／沿用短摘／未開原文；由材料狀態生成範圍摘要，人工覆核 |
| 版本交接多且易漂移 | 多份 proposal 合併後再縮稿、修訂、匯出、接入；CMS v2 標題仍含工作流標示，之後網站顯示層移除 | 公開標題與審稿狀態分欄；統一發布包含 display title、正文與來源，對照 CMS、預覽及正式頁 |
| 每場賽事的公開接入仍需工程操作 | runner-copy loader、hash 及 export check 有 RMAC 專用邏輯 | 通用「已確認匯出 → 驗證 → 公開檔 → 預覽」轉換，沿用既有確認與部署批准，不為每場改程式 |
| 搜尋量與評分所需資料不對齊 | 14 則材料經合併仍不能支持三項數字評分；補給、寄存及交通體驗不足 | 在搜尋頁顯示每個主題缺哪些具體觀察；下一輪針對缺口找材料，無材料維持未知／未評 |

五類 reviewed、兩類 no_results 只是最後保存狀態；不表示每平台已窮盡，亦不對搜尋完成程度作重新認證。

## 下一版優先次序

### 第一批：縮短審稿及公開交接

1. 一個賽事工作頁：七類來源、缺口、proposal、目前草稿、網站稿及下一動作。沿用舊表與資料庫，避免另起第二套工作狀態。
2. 同頁列 proposal 與候選網站稿的完整內容及差異。接受 proposal、確認網站稿仍各綁定確切版本；可同輪覆核，減少逐次要求「下一步」。內容改動才需重新確認。
3. 公開標題與審稿狀態分開；確認前檢查工作流字樣、人名／帳號／機構名及逐項來源。名稱檢查只提示，保留人手判斷及原始 URL。
4. 通用匯出轉換及發布 manifest：賽事 ID、CMS 版本、來源與公開內容 hash、GitHub commit、部署版本、網址。對照完整段落及來源，保證發出去的是看過的版本。不要為 display title 留永久字串修補。

驗收：換另一場賽事毋須修改 RMAC loader；有來源／正文變更不能沿用舊確認；已確認稿不含內部狀態字樣；私人材料與候選評估不進部署包。

### 第二批：令研究可以恢復，令 AI 少搬資料

1. 每平台多次搜尋記錄及恢復點，將 Cloudflare／其他驗證與登入需要分清，避免「登入完成＝研究完成」。
2. 材料到主題敘述的對應：短摘、解讀、材料 ID、讀取版本、屆次、採用／排除原因、同作者關聯。先用現有備註落實 SOP，再按使用量加欄位。
3. 補齊受限 agent API 的 proposal、coverage 及網站草稿寫入；不增加 AI 確認／匯出／發布權。寫入保留 expected_revision、idempotency_key、角色與模型 audit，不靠 UI 身份或直接 SQLite 寫入。
4. Agent context 限定賽事、屆次及變更版本。現有受限 context 已按賽事年分篩選；舊可信 CLI context 仍讀全工作區。增加分頁／自某版本以來的變更，減少將無關材料帶入對話。

驗收：中斷後可從同一來源續查；同一材料重試不新增；重讀只更新該材料；AI 操作身份可追溯且不能代人批准。

### 第三批：可靠營運後再擴量

1. 以真實備份副本演練還原，另作私人異地備援；目前本機三庫快照不等於雲端備份。
2. 新私人賽事到公開賽程的獨立合約及確認流程；現有新增頁只建私人研究賽事，未自動發布 catalog。
3. 評分做獨立證據表及待確認修訂，沿用三項準則。先補資料，不用情緒分析或留言票數自動打分。
4. 要多人／遠端 CMS 時才加真正登入、角色及存取隔離。公開靜態網站可運作，不代表本機 SQLite 後台已適合直接放上網；現況是單一本機可信操作者。

## 工作方式先改，毋須等 CMS 大改

- 開始先記任務範圍、已有批准及交付上限；先恢復既有材料，避免每輪重新全查。
- 七類首輪都做，遇登入立即記住斷點並請協助；之後按未知主題擴查，不無限重搜同一熱門平台。
- 同批材料整合一份 proposal；以材料 ID 引用，補查另存差異，不為每平台另起整篇稿。
- 一次交完整可覆核稿與差異；分清文字確認及發布批准，對同一版本不反覆索取相同決定。
- 用 [SOP](RACE_RESEARCH_SOP.md) 的交付簡表，接手或新對話只需讀最新狀態與變更。

## 衡量是否更有效率

下一至三場記錄每場的人手點擊／跨頁次數、重複輸入次數、覆核往返、新增及重複材料、因版本過期退回次數、登入等待與實際研究工時、發布內容偏差。先建立基線再比較，不預先承諾節省百分比；登入等待與操作成本分開計算。

本評估建立時只新增評估、SOP 及個人可重用 skill。其後按營運者要求完成第一批本機 CMS 改動：集中工作頁、完整覆核與網站稿差異、公開標題檢查、通用交接檔及 HTML 預覽，詳見 COMMENT_RESEARCH.md。自動公開資料接入／runtime loader 通用化、agent API 擴充及第二、三批仍未實作；研究狀態、稿件批准、評分及正式網站未因本輪 CMS 更新而改動。
