# 賽事研究 → AI proposal → 網站稿 SOP v1

適用於本 repo 的私人 CMS。沿用現有系統，不把本文件中的建議當成已實作功能。產品操作及欄位合約見 [COMMENT_RESEARCH.md](COMMENT_RESEARCH.md)，評分另見 [RATING_METHOD.md](RATING_METHOD.md)。

## 1. 定義本輪任務

先記錄賽事 ID、屆次、日期（可未知）、組別、名稱變體、現有材料、研究目的及交付上限。分清「補查缺口」「重讀既有材料」「完整首輪研究」，不可把其中一種描述成另一種。

預設交付至待覆核網站稿及本機預覽；不自動 commit、push、發布、部署或更改網站訪問設定。若本輪已有明確授權，依其範圍繼續，不重複要求批准。原文、待覆核材料及操作檔只放 `.editorial-private/`，不放進公開 source imports／assets。

## 2. 開啟或恢復工作區

- 先讀 repo 的 `AGENTS.md`、本 SOP 及 CMS 文件；檢查工作目錄與版本，保留既有修改。
- 用 Node 24+ 啟動 `npm run content:manage`，使用終端實際顯示的本機網址。先確認是否已有相同真實工作區在執行，避免開錯資料庫；示範資料庫與真實資料庫分開。
- 賽事卡可開啟「賽事工作頁」，按研究屆次集中查看來源、proposal、網站全文及差異；公開標題與工作狀態分開。已確認稿可下載通用交接包及開獨立 HTML 預覽，仍不會自動寫入正式網站。
- 沿用現有賽事及材料 ID；不存在才在 CMS 新增私人賽事，不借用相近比賽 preset。私人新增不代表已加入公開賽程。
- 讀取既有 proposal、草稿、網站稿版本、七類來源狀態及未解事項；沿用現有私人備份功能保存快照，不將備份公開。
- AI 寫入優先使用現有受限 HTTP API，權限、格式見 CMS 文件。它目前沒有七類進度／網站稿寫入及 proposal 提交的完整受限介面；欠缺部分沿用現有本機 UI 或可信宿主的 proposal CLI，明確區分操作方式。不要繞過權限白名單或直接改 SQLite。

## 3. 每類來源先查一輪，再按缺口擴查

以 `scripts/research/sources.mjs` 當前設定為準。目前包括 Threads、Marathon’s World、Facebook 公開帖、Instagram 公開帖、YouTube Vlog／留言、運動筆記、個人網誌。官方資料另外核對賽事身份及基本安排，不能代替以上類別。

每類先以完整賽名＋年份搜尋，再按需要使用名稱變體、英文／距離字詞、站內搜尋及適用排序。排除同名海外賽事與其他屆次。搜尋摘要只作候選，須打開原帖、留言或文章才記作已讀。影片記清楚看了標題、說明、字幕、留言或哪段影像；只讀說明不能稱看完影片。

每次嘗試記錄：

| 欄位 | 記法 |
| --- | --- |
| 搜尋 | 實際字詞、索引／站內、篩選及排序、已載入範圍 |
| 時間 | 實際查閱時間及時區；與保存時間分開，不以批次寫入時間冒充逐來源閱讀時間 |
| 連結 | 搜尋／清單頁與原文連結分開；CMS `links` 只放其驗證接受的原文 URL，其餘記於 notes |
| 結果 | 找到線索、已讀原文、可採用材料分開描述，記材料 ID／排除理由 |
| 限制 | 登入、驗證、載入範圍、未讀回覆、未看影像、屆次不明等 |

沿用六種狀態：`not_started`、`searching`、`awaiting_login`、`reviewed`、`no_results`、`inaccessible`。`reviewed` 只表示列出的原文已讀，不代表全平台搜尋完成、有可採用親身材料或足以評分。沒有原文但完成指定搜尋可記 `no_results`，必須說明搜尋邊界。

遇登入：保留原分頁，記 `awaiting_login`，請擁有人在原站完成；不索取密碼、驗證碼、Cookie 或 token。等待時繼續其他來源。擁有人回覆後回到同一平台、同一查詢續查；回覆「已登入」本身不是完成研究。人手驗證同樣交回擁有人，不繞過。

每類完成合理首輪及必要名稱變體後，若沒有新增可用材料，記本輪停止點；不要無限重搜。尚有待登入或存取失敗時可交付帶缺口的草稿，但不得聲稱研究完成。不要由「無結果／不可存取」推斷跑手沒有意見。

## 4. 材料先保存，後整理

每則保留原文短摘、原文 URL、平台、屆次／組別依據、發布日期（未知留空）、本輪讀取範圍及材料 ID。私人作者識別可用於去重；公開稿只用中性來源編號，URL 保留原始出處。

把原文、AI 意譯、編輯判斷分開。官方／賽前介紹、親身自述、旁觀／祝賀、影片線索分開標記；上載年份不等於賽事年份。標明是本輪重讀、沿用舊短摘或尚未開原文，不用一句「全部未重讀」概括不同材料。

以既有 URL／內容識別去重並保留版本；同作者主帖、回覆、跨平台轉載不當獨立跑手。身份未明就保留未知，不猜人數或統計共識。只把與賽事、屆次及主題相關的材料送入草稿，其餘保留排除理由。

## 5. 建立 AI proposal

優先整合成本輪一份 proposal，而非每個平台各寫一份。補查只另存新版本或新增建議，註明與前版差異；舊版不刪除、不覆寫已確認稿。

包括研究範圍、五項正文、來源及材料 ID、逐項觀察限制、未知事項、七類覆蓋摘要、未完成項目，以及相對上一版的改動。更新時帶當前 `expected_revision`，重試沿用同內容的 `idempotency_key`；遇版本衝突先重新讀取，不能硬蓋。

人工接受 proposal 只保存私人草稿。研究資料的 keep／exclude、proposal 接受、網站文字確認與發布批准是不同動作；AI 可以提出建議，不代擁有人建立批准收據。

## 6. 形成網站稿並覆核一次完整版本

由已保存草稿建立網站稿，固定五項：賽道、補給、寄存、交通、大會安排。每項都保留正文、來源、限制；不足明示未知。不要以缺少負評推成滿意，或將難度當服務質素。

公開標題不寫「候選／待覆核／未部署」；工作流狀態放在 CMS 狀態欄及本機預覽提示。公開文案不出人名、帳號或機構／傳媒名；使用「來源1」等標籤，原文 URL 不因去名而刪除。原文來源頁本身仍可顯示作者，不承諾來源匿名。

交付一個可覆核頁面：完整網站文字、與前版差異、來源及限制、覆蓋缺口、確切版本及雜湊。可以在同一輪提供 proposal 與網站稿，仍分開記錄各自確認對象；無新改動不重複要求相同版本的確認。

若依據草稿、賽事或來源紀錄更新，沿用現有 stale-basis 檢查，重新保存受影響網站稿再確認。來源未完成時要清楚列缺口；只有擁有人明確認可保留未知，才使用 CMS 的未完成來源確認選項，不能代勾選。

評分只在使用者要求時另開評估，沿用 `src/lib/rating-policy.ts` 三項準則及其證據要求。資料不足為 null／未評，不當零分、不設總分；未經完整指定修訂批准，不加入 `editorial-reviews.json`。五項網站分享不等於五項評分。

## 7. 交付及可選發布階段

預設交付：七類來源表、待覆核 proposal、網站稿指定版本、未知及後續待辦、本機預覽。報告本輪新增／沿用／排除的材料，不把材料數當跑手數。列明仍待哪一個人的哪一項決定。

擁有人確認文字後，可按授權透過 CMS 匯出指定已確認版本；匯出仍是私人交接檔，不是發布批准。網站接入、commit／push、部署各依當前已授權範圍進行。現行公開接入仍有 RMAC 專用綁定，新賽事不能直接套用該檔或改其 race ID 當完成。

若獲授權進入發布，依 `docs/DEPLOYMENT.md` 及現有部署工具：核對版本、來源、去名、未知及評分；通過 editorial、建置、export 及 HTTP 檢查；從乾淨來源打包，排除私人材料。部署後對照正式頁標題、正文、來源連結、限制、評分狀態及版本，保存實際結果，不把 GitHub push 當作已部署。

## 本輪交付簡表

- 賽事／屆次／組別、任務範圍：
- 七類來源逐項狀態、實際查閱時間、搜尋及存取限制：
- 材料：本輪新增／沿用／排除；身份及屆次未知：
- Proposal ID／版本；草稿 ID／版本：
- 網站稿 ID／版本／雜湊；本機預覽：
- 本輪變更、未知及未完成來源：
- 本輪已獲確認的對象、仍待確認的對象：
- 是否允許匯出／commit／push／發布／部署；實際執行結果：

實際數值及研究紀錄填在 `.editorial-private/` 或 CMS；本 SOP 不保存個案原文。

## 網站驗收交接

網站稿交付驗收時依 [網站驗收 SOP](SITE_QA_SOP.md)：帶齊賽事 ID、材料屆次／組別、proposal／網站稿 ID 及版本、評分版本／未評、可查的人工確認狀態、來源／限制／未知、前版變更、目標頁及授權上限。既有 CMS 紀錄可用引用，不重貼私人原文；缺項標未知，不代產批准。

先用 `npm run check:content` 或本機 HTTP 模式核對已接入的選定稿，再作瀏覽器行為驗收。目前指令只覆蓋已選定兩場 2025 稿，新研究稿未接入時記為不在覆蓋範圍，不能冒稱已通過。驗收通過不等於接受 proposal、確認文字或批准發布。
