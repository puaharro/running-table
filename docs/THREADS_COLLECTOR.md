# Threads Collector V0.1

先收集、保存原始證據，再另行研究評分。這個版本是私人 CLI，不會把留言、使用者名稱或分析發佈到網站；沒有情緒分析、LLM 分類、賽事評分或自動確認相關性。

## 啟動

需要 Node.js 24 或以上（與網站 CI 相同）；使用內置 `fetch` 和 `node:sqlite`，無須額外 npm 套件、Python 或資料庫服務。第一次可先用 `node --version` 確認環境。

npm 收集指令會用 `--use-system-ca` 加入作業系統信任憑證，保留正常 TLS 驗證。

在 repo 根目錄的 `.env.local` 加入：

```dotenv
THREADS_ACCESS_TOKEN=your_threads_user_access_token
```

也可以由執行環境提供同名變數，環境值優先。不要把真實 token 貼到程式、測試、Git 或聊天記錄；這個變數只供 CLI，沒有 `NEXT_PUBLIC_` 前綴。

第一批以香港賽事為主，先收集渣打香港馬拉松：

```sh
npm run collect:threads -- --race "Hong Kong Marathon" --year 2027 --keywords-file docs/examples/threads-hong-kong-marathon.json
```

已準備以下香港賽事關鍵字檔。這些只是待驗證的搜尋別名，不代表已收集資料或確認相關性；不同賽事分開建立 run，避免把所有香港賽事混成一場。

| 賽事                               | 關鍵字檔                                        |
| ---------------------------------- | ----------------------------------------------- |
| 渣打香港馬拉松（含「渣馬」等別名） | `docs/examples/threads-hong-kong-marathon.json` |
| 港珠澳大橋（香港段）半馬拉松       | `docs/examples/threads-hzmb-half-marathon.json` |
| 美津濃香港跑步祭                   | `docs/examples/threads-mizuno-hk-run-fest.json` |
| UNICEF HERO RUN 超能跑             | `docs/examples/threads-unicef-hero-run.json`    |

主賽事、5 公里海濱跑及少年跑可能共用渣馬關鍵字；收集階段不會自動歸入組別或當作已核實參賽體驗。「UNICEF 慈善跑」亦可能命中過往不同活動，保留原文待之後審核。

自訂賽事及多個關鍵字：

```sh
npm run collect:threads -- --race "Hong Kong Marathon" --year 2027 --keyword "香港馬拉松" --keyword "Hong Kong Marathon" --search-type RECENT
```

不指定關鍵字時只使用 `--race` 的原文；不會自動生成翻譯。`--keywords-file` 是 UTF-8 JSON 字串陣列，可以與重複的 `--keyword` 合併，重複關鍵字只查一次。預設每頁 100 筆，可用 `--page-size 1..100` 調整。所有參數見 `npm run collect:threads -- --help`。

`--year` **只是收集計劃的目標屆次標籤**，不會把留言自動認定為該年參賽經驗，也不會限制 post 發佈日期。包含「2027」的關鍵字可另外加入搜尋。搜尋命中未經相關性審核；即使是其他年份、轉貼或招募文章，也保留原文供下一階段判斷。

## API 存取與界線

實作按照 Meta 官方 Threads Postman 範例的 `keyword_search` 和 `/{thread_id}/conversation`，使用 OAuth Bearer token、指定欄位及分頁。參考：

- [Meta 官方搜尋請求範例](https://www.postman.com/meta/threads/request/34203612-b3b2c12a-7ce6-4d86-a3c6-6d31e3b66ea1)
- [Meta 官方 conversation 範例](https://www.postman.com/meta/threads/documentation/dht3nzz/threads-api?entity=request-34203612-74fb48b1-ad1a-480e-b200-4dcdb8126a2f)
- [Meta 權限及 access token 文件](https://developers.facebook.com/documentation/threads/get-started/get-access-tokens-and-permissions)

必須在自己的 Meta App Dashboard 核對有效的 Threads user token、`threads_basic`、搜尋所需 `threads_keyword_search` 的審批與存取級別，以及讀取 conversation 所需的權限（包括適用的 `threads_read_replies`）。有 token 不代表可以讀取所有第三方貼文的回覆。需要用有權限的真實帳號先做小批驗證；本地自動測試不能證明 Meta 已批准存取。

這是「收集官方搜尋結果及 API 允許讀取的公開 conversation」，不是全平台完整封存。空結果只表示 API 沒有返回內容；`complete` 只表示本次 API 分頁已走完，不證明相關性、年份、權限涵蓋範圍或所有公開回覆均已取得。被刪除、隱藏、不可存取的內容可能缺漏。沒有使用登入牆繞過或第三方爬取服務。

搜尋命中若本身是回覆，會保存該命中，並用 API 返回的 `root_post.id` 收集 root conversation。父子關係保留 `replied_to.id`；缺漏父節點或沒有 parent 欄位時不會虛構上層或深度。來源 permalink 沒有返回時保持 null。

## 保存及續跑

### 未有 token：先用私人資料檢視工具

```sh
npm run inspect:threads -- --demo --serve
```

這個指令不讀取 `.env.local`、不使用 token、不呼叫 Threads API，亦不寫入正式收集 SQLite。它在記憶體建立**虛構香港路跑**資料，模擬 2 個 posts、4 條留言、父子回覆、未知 parent 及無法取得某個 conversation，然後輸出一份標示「虛構示範」的 HTML。打開終端顯示的 `Private preview` 網址即可試用。

頁面支援搜尋留言／作者／關鍵字／ID、只看未完成的討論、展開原始欄位，以及查看搜尋來源、收集進度和錯誤。示範不能用來評價任何真實香港賽事。

真正收集資料後：

```sh
npm run inspect:threads -- --list
npm run inspect:threads -- --run RUN_ID --serve
npm run inspect:threads -- --run RUN_ID --format json
```

`--list` 列出可檢視的 run ID；`--db FILE` 可以選擇另一個已有的私人 SQLite。真正資料以 read-only 模式開啟，按該 run 的已提交原始頁面重建，不受後來 run 對同一 post/comment 的更新影響。這與 collector 的 `--status` 使用最新 username 計算帳號數不同；檢視報告採用該 run 的 username，數字可能不同。

HTML／JSON 預設寫入 `.editorial-private/threads/reports/` 的新檔案。可以用 `--output FILE` 指定私人目錄內的檔名，副檔名須符合格式；已有檔案不會被覆寫。JSON 包含 run、統計、搜尋詞、原文、父子 ID、來源及收集時間，沒有分數。

預覽只監聽 `127.0.0.1`，只提供這一份報告，不提供 SQLite、私人目錄或其他檔案；Ctrl+C 停止。HTML 的搜尋在本機執行，沒有外部字型、分析碼或網絡請求。原文連結只接受 HTTPS Threads 網址，點擊後才會前往原站。報告應留在私人目錄，不要提交 Git、放入公開資產或部署封裝。

### 有 token：收集進度

預設 SQLite：`.editorial-private/threads/collector.sqlite`。`--db FILE` 可以選擇本 repo `.editorial-private/` 之內的其他檔案。這個目錄及 `.env.local` 都已被 Git 忽略。原始內容不能放進 `public/`、`src/data/`、部署封裝或提交到 Git。

每次新收集會建立一個 run ID，先輸出到 stderr；最後 stdout 是 JSON 統計，包括：

- `posts_discovered`：本 run 搜尋命中的獨立 post ID。
- `conversations_fetched`：已走完分頁的獨立 root conversations，包括 API 返回空清單的 conversation。
- `comments_collected`：本 run 已存入的獨立 comment ID。
- `unique_accounts`：本 run posts/comments 中不同 username 的數量，不等於已驗證參賽者人數；缺 username 的內容不計。
- `failed_requests`：本 run 失敗的 HTTP／網絡嘗試次數，包含重試後成功的嘗試；儲存或分頁協議錯誤另記錄在 `api_errors`。
- `pending_queries` / `pending_conversations`：仍未完成的任務數，包含失敗的任務。

續跑只提供原 run ID（及需要時相同 `--db`），不能同時改 race、year、keywords 或搜尋設定：

```sh
npm run collect:threads -- --resume RUN_ID
npm run collect:threads -- --status RUN_ID
```

`--status` 不使用 API，也不需要 token。已完成 run 的 resume 不會發出請求；想更新舊 conversation 要執行新的收集 run。每個新 run 都會重新搜尋及讀取 conversation，並以平台 ID upsert 最新內容。

每一頁的資料、來源關鍵字與下一頁游標在同一 SQLite transaction 提交。正常 Ctrl+C 會停止請求或等待，標記 `interrupted`，然後可以 resume；程式被強制終止也不會提交半頁，最後未提交的頁面下次重讀。過期的 API cursor 會記錄為失敗；如 Meta 不再接受舊 cursor，請開新 run 重搜，以平台 ID 去重。

CLI 會以 `<database>.lock` 阻止同一 DB 同時執行，正常退出時釋放。強制終止／斷電後如果報 `database_locked`，先查看 lock 裏的 PID，確認沒有收集程序仍在執行，再刪除該 `.lock` 檔並 resume。不要刪除 SQLite 檔案。

退出碼：0 = API 分頁完成或 status/help 成功；2 = 參數／token／存取失敗或部分完成；130 = 使用者中斷。失敗的 post 不會阻擋其他可讀 conversation；身份、權限及限流錯誤會停止整批，避免浪費請求。

## 資料表

| 表                           | 用途                                                      |
| ---------------------------- | --------------------------------------------------------- |
| `races`                      | 賽事名稱與目標屆次標籤                                    |
| `collection_runs`            | run 狀態、搜尋設定及起訖時間                              |
| `search_queries`             | 每個 run 的原文關鍵字、游標與狀態                         |
| `threads_posts`              | 搜尋命中的最新原文、ID、作者、時間及 permalink            |
| `threads_comments`           | 最新留言、root ID、直接 parent ID 及來源欄位              |
| `post_discoveries`           | 同一 post 被哪些關鍵字發現及時間                          |
| `run_posts` / `run_comments` | 每個 run 的 conversation 進度與留言 ID                    |
| `collection_pages`           | 每次已提交 API 頁的原始 data 陣列及收集時間；保留歷史版本 |
| `api_errors`                 | 失敗分類、HTTP 狀態、API code、嘗試次數及時間             |

`threads_posts` / `threads_comments` 的 `first_collected_at` 保留首次收集時間，`last_collected_at` 是最後觀測時間；平台 timestamp 另存，不混用。每頁 raw data 另外保存，因此新 run 的 upsert 不會抹掉先前收集的原文版本。run 統計的 ID 歸屬固定，但 username 等欄位採用最新觀測值。

錯誤紀錄不保存 API 原始訊息、request URL、header、token 或完整 paging URL。分頁只使用下一頁 cursor，請求固定發到 Threads API，拒絕 HTTP redirect 和非預期 host/path。429、5xx、網絡錯誤及可重試 API code 最多重試 4 次，加上初次請求共 5 次；指數退避及 `Retry-After`，超過 60 秒的 server 等待要求會停止並留待稍後續跑。每次請求超時 30 秒，預設間隔 250ms；實際帳戶配額仍以 Meta 回應為準。

## 未有 token：手動匯入香港賽事原文

```sh
npm run import:threads
```

開啟終端顯示的本機網址（預設 `http://127.0.0.1:3332/`）。這是空白的真實手動工作區，不會自動載入虛構留言或讀取 token，也不會連線來源網址。

1. 選擇香港賽事及收集目標屆次。這只是整理批次標籤，不會當成留言的已核實賽事／年份。
2. 選主帖或留言，貼上原文及完整 HTTPS Threads 來源連結；作者未知可留空。可以另外填寫來源備註。
3. 留言有獨立連結時，另外填主帖連結；只有主帖連結時，請明確選「只有主帖連結」。
4. 父回覆未確定時保持未知；只有你明確知道直接回覆主帖，才選「直接回覆主帖」。回覆另一留言則填父留言連結。
5. 按「保存原文及來源」，等到伺服器回覆已保存。未保存內容離開頁面時會由瀏覽器提示。
6. 在「已保存批次」按「清理、去重並準備人工覆核」，再開清理結果或直接逐條覆核，儲存保留／排除、賽事、年份及備註。

匯入頁支援現有四場香港賽事 preset。每個 preset／目標年份有獨立批次；原文、輸入的來源網址、作者、備註、父子關係及匯入時間保存於 `.editorial-private/threads/import/manual.sqlite`。原文不會被清理文字覆寫，沒有提供發佈時間時保持未知。

相同來源的目前版本重貼不會重複新增；不同內容／來源備註／關係等變更會追加新觀測版本。若先改文、後再貼回早前版本，也會保存這次回復。清理取每個本地來源最新觀測，舊版本仍留在資料庫，可用「匯出全部原文版本」取回。

手動來源使用清楚標示的本地 ID，不會把 URL shortcode 或本地文字指紋冒充 Threads API ID。`threads.net`／`threads.com` 及 `/t/代碼`／`/@名稱/post/代碼` 以相同 shortcode 辨認同一獨立來源；原來提交的完整 URL 保留，點擊用的連結去除 query／fragment。來源僅限支援的 HTTPS Threads 貼文格式，不會因此宣稱連結確實存在、文字完整或作者已驗證。

只有主帖來源的留言，原文、作者、主帖及明確回覆關係構成本地觀測身份；沒有獨立留言 permalink，介面會標示「查看來源主帖」。這種情況無法區分同一作者在同一主帖發出完全相同的兩條實際留言，不能把本地觀測數當成完整平台留言數。修改原文亦可能形成另一份本地觀測，交清理與人工覆核判斷，不能視為已驗證的留言編輯。

### 從匯入接到清理、覆核及匯出

- 清理沿用原文／父子鏈規則，賽事及年份選單不會代替原文依據。每次準備會建立不可變的清理快照；修改匯入資料或更新規則後，新的快照由未覆核開始，不會自動繼承舊決定。
- 在批次卡片的「過往清理及覆核快照」可重開已保存版本；舊快照、原文及舊覆核仍可追溯。
- 預設覆核結果獨立保存於 `.editorial-private/threads/import/manual-reviews.sqlite`，與原始 collector SQLite、另一個私人覆核工作區分開。
- 可匯出全部原文版本、清理 JSON，或人工覆核 JSON。清理 JSON 亦可交給既有 `review:threads -- --input FILE`，但它使用另一個預設覆核資料庫；如要繼續原有匯入頁的覆核，請直接用批次卡片連結。
- `mode: manual`、`ingestion_method: manual_paste`、`source_verified: false` 會保留到清理及覆核輸出；不能當作 API 抓取或已核實參賽經驗。
- 清理規則版本已更新為 `hk-clean-v2`，以區分本地手動來源與平台 ID 去重。舊規則快照及其覆核保持原樣。

```sh
npm run import:threads -- --demo --port 3333
```

這個指令開啟獨立的虛構資料測試工作區，預設也是空白；只用來貼測試內容，不會填入真實工作區。原文及覆核分別保存於 `import/demo.sqlite` 與 `import/demo-reviews.sqlite`。`--db`／`--review-db` 可選擇私人目錄內的獨立檔案；`--port 0` 自動選空閒埠。停止服務後，備份原文與覆核兩個 SQLite 即可保存整個工作區。

## 香港賽事留言清理（不評分）

```sh
npm run clean:threads -- --demo --preset hk-marathon --serve
npm run inspect:threads -- --list
npm run clean:threads -- --run RUN_ID --preset hk-marathon --serve
npm run clean:threads -- --run RUN_ID --preset hk-marathon --format json
```

未有 token 可以先跑虛構 demo。真正收集後使用 run ID；清理只以 read-only 模式讀取該批已保存原始頁面，不會連線 API、修改 SQLite 或刪除留言。`--preset` 必須明確選擇：

| Preset            | 目標賽事                 |
| ----------------- | ------------------------ |
| `hk-marathon`     | 渣打香港馬拉松           |
| `hzmb-half`       | 港珠澳大橋香港段半馬拉松 |
| `mizuno-run-fest` | 美津濃香港跑步祭         |
| `unicef-hero-run` | UNICEF HERO RUN 超能跑   |

demo 只示範 `hk-marathon`，資料全部虛構；其他 preset 可用真實 run 或測試資料。目標屆次沿用 run 的標籤，不能視為已核實參賽年份。搜尋關鍵字不會當作相關性證據，賽事別名採用有限字典（並非涵蓋所有香港比賽或所有寫法）；沒有明確依據的內容放入待覆核。`UNICEF 慈善跑` 這類較廣泛搜尋詞不會直接確定為 HERO RUN。

### 處理規則

- 清理文字：Unicode NFKC、移除 BOM／零寬空格、整理空白與換行。保留 emoji 組合連接符、標點、網址、語意及完整 `raw`，不把繁簡字或近似句自動合併。
- 平台 ID：同一 ID 同時被搜尋及 conversation 取得，只計一個證據身份，優先保留 conversation 觀測；兩份原始觀測仍在輸出。如文字版本不同會另標記。
- 同作者同討論：至少 20 個 Unicode code points 的文字，經空白正規化後完全相同才標記重複。不同 ID 的短句或 emoji 不自動合併。
- 跨作者／跨討論：相同長文字只標記可能重複，移至待覆核，沒有 fuzzy match 自動排除；作者未知也不自動合併。
- 相關性：原文明確提及目標賽事，或可沿完整父子鏈追溯至該賽事，才列為相關。父節點缺漏、循環、跨 root 不會建立繼承依據；沒有直接名稱的短句／emoji 仍需覆核。由父帖取得語境不代表已確認作者參賽。
- 跨年／混合賽事：明示年份與目標屆次不同、父回覆年份不同、比較或否定名稱、多場賽事混合，都放入待覆核；發佈 timestamp 不會當作參賽年份。
- 明確其他賽事：字典識別到其他已知賽事，且沒有目標賽事依據時標為無關。未知活動名稱仍待覆核，不會因為沒命中字典就排除。
- 推廣／垃圾內容：有限規則只標記疑似項目並交人工覆核，不聲稱辨識 bot、主辦方或真正參賽者，也沒有情緒分析或評分。

### 結果與稽核

每項有 `disposition`（`keep`／`review`／`exclude`）、`relevance`、判斷依據、原因代碼、`duplicate_of`、`possible_duplicate_of`、原文年份、文字指紋及完整 raw。`keep` 是相關且未被去重的候選資料，並不表示已通過人工審核；`review` 是人工覆核清單；`exclude` 是重複或明確無關的觀測，仍然留在結果內。

HTML 可依結果篩選並展開原始欄位；JSON 的 `records` 包括所有觀測，下游可按 `disposition` 取出候選資料。預設輸出 `.editorial-private/threads/cleaned/` 的新檔案，不覆寫舊檔。`rule_version` 與 `source_digest` 記錄規則版本及來源摘要；相同輸入可重跑得到相同逐項判斷。規則或字典變更需要更新版本，重新整理原始資料。

這是第一版可解釋規則，需要用真正香港賽事資料抽樣覆核後再調整。沒有 token 時，示範結果不能當作真實資料的準確率驗證。

## 逐條人工覆核（不評分）

```sh
npm run review:threads -- --demo
```

未有 token 時可直接試用虛構 demo。預設網址 `http://127.0.0.1:3330/`，Ctrl+C 停止；`--port 0` 可自動選擇空閒埠，網址會顯示在終端。重新執行同一 demo 指令會開啟原來的示範來源及已儲存決定，不會每次生成另一批示範資料。

真正資料先產生清理 JSON，再指定該檔案：

```sh
npm run clean:threads -- --run RUN_ID --preset hk-marathon --format json
npm run review:threads -- --input .editorial-private/threads/cleaned/RESULT.json
```

`RESULT.json` 請改為上一個指令實際顯示的輸出路徑。人工覆核只讀取這個清理快照，不直接修改原始收集 SQLite、清理 JSON 或公開網站資料。

### 使用方式

1. 用搜尋欄或「未覆核／人工保留／人工排除」篩選找到項目；所有項目開始均為未覆核，自動保留／排除不會當成人工決定。
2. 展開原文與自動判斷依據，查看重複指向、父回覆 ID、賽事命中及原文年份。
3. 選擇保留、排除，或還原為未覆核；可以修正賽事名稱（支援自由輸入及四場香港賽事建議值）、年份（1900–2200）及備註。賽事／年份留空代表未確定。
4. 按「儲存這條覆核」。只有出現「已儲存 · 第 N 版」才代表伺服器已確認寫入 SQLite；欄位變更而未儲存會顯示「尚未儲存」。關閉或重新載入有未儲存修改的頁面時，瀏覽器會提示。
5. 重新載入會回復已保存資料；「覆核修改歷史」保留每次決定、賽事、年份、備註及儲存時間。
6. 按「匯出覆核結果 JSON」，得到完整原始／自動判斷、人工修正及歷史。`confirmed_decision` 為 `pending` 的項目仍未獲人工確認，不能用自動結果代填。

每次修改只作用於該項，不會自動套用父帖、子回覆、同 ID 的另一種觀測或重複項目。即使人工選擇保留一個自動標記為重複的觀測，原本 `duplicate_of` 仍保留供後續追溯。預設顯示的賽事與年份是清理流程的建議值，儲存前需要你確認。

### 保存、版本及資料隔離

- 正式覆核預設保存於 `.editorial-private/threads/reviews/manual.sqlite`；虛構 demo 使用獨立的 `demo.sqlite`。可用 `--review-db FILE` 選擇私人目錄內另一個獨立資料庫，不能指定原始 collector SQLite。
- `review_datasets` 保存不可變的輸入快照；`manual_decisions` 保存目前決定；`manual_review_events` 保存每次修改歷史。恢復未覆核亦會新增版本，舊版本不會消失。
- 同一份證據與規則重跑清理、只改變報告產生時間，不會失去覆核；原文、規則、目標賽事或其他輸入內容改變時，建立另一個資料批次，不會把舊決定靜默套到新證據。
- 儲存採用 transaction，把目前決定與歷史一起提交；兩個視窗同時修改同一項時，過期版本回傳衝突，要求重新載入，避免覆蓋新決定。
- 覆核頁只監聽本機；只有同源頁面帶本次頁面 token 的 JSON 儲存請求才可寫入。頁面及匯出均不公開，也不呼叫 Threads API。
- 這是本機資料覆核記錄，不驗證操作者身分，亦不是賽事評分、法律審查、公開內容批准或自動發佈流程。

停止程序後，備份獨立的 review SQLite 即可保留來源快照與全部覆核歷史；JSON 匯出可用來查看及另行處理，目前沒有覆核 JSON 匯入功能。

## 人工確認後的留言資料集（不評分）

在逐條覆核頁按「查看已確認留言資料集」，或由手動匯入批次卡片進入「已確認資料集」。每份資料集只對應一個明確的清理／覆核快照，不會自動跨舊快照合併或套用舊決定。

頁面按人工覆核後的賽事與年份分組，可搜尋原文／作者／賽事及篩選年份：

- 只有已保存 `keep` 的人工決定會進入整理；自動保留、未覆核及人工排除不會代替人工確認。
- 使用你在覆核表填的賽事及年份，不代填原批次目標。缺賽事、年份或可用原文時，留在「已保留但需要再處理」。
- 同一來源身份的多份觀測，只有原文及修正後賽事／年份一致才合併為一個可用項目，並保留每一份原始觀測、人工決定、版本及歷史。任一項有衝突則整組待處理，不會擅自選較新的決定。
- 不同身份即使被自動規則標為可能重複，只要你都保留就不會自動刪去；會附提示，供你回覆核頁再決定。
- 內置香港賽事別名只用於分組，逐項保留你輸入的原名。自訂名稱亦可保留，但會標示地區未確認，不會自動當成香港賽事。
- 手動來源的未驗證標記、只有主帖來源的範圍，以及本地文字身份，會保留到資料集。整理後項目數不代表獨立跑手或完整平台留言數。

「下載已確認 JSON」包括可用項目、待處理原因及全部人工保留觀測的稽核資料；「下載可用項目 CSV」只含資料齊全且沒有身份衝突的可用項目。匯出包括整份快照，不受頁面的搜尋／年份篩選影響。CSV 的不可信文字會做試算表公式防護及引號／換行處理；完整原文仍保留於 JSON，沒有情緒分析或賽事分數。

覆核讀取使用一致的 SQLite transaction，下載有 `review_fingerprint` 追溯目前人工版本。頁面下載連結綁定該版本；如果另一視窗改了覆核，舊預覽下載會回報衝突，要求重新載入資料集。已下載的檔案是當時的版本，不會被之後的覆核自動改寫。

正式及示範工作區分開，只有私人本機頁面與下載；不會發布到網站或 Git。

## 已確認留言的主題分類（不評分）

在「已確認留言資料集」的可用項目內，可查看或修正多選主題：交通、寄存、水站、賽道、賽事組織；另有只供人工選擇的「其他」。只有已人工保留、賽事年份齊全且沒有原文衝突的項目可做主題覆核，未覆核／排除項目不會被代為確認。

1. 查看每條原文下的自動分類依據：規則 `hk-topics-v1` 只按該條原文的中英文詞句命中，顯示原字及片段；來源連結、父帖內容和賽事名稱不參與分類。例如「冇水站」仍屬水站討論，不判斷好壞。未命中不代表不相關。
2. 在「修正主題」勾選一個或多個標籤，選「已人工確認所選主題」並儲存；確認時至少選一項。模糊內容可選「未確定，保留待判斷」，容許暫時不選標籤。「未覆核／還原自動建議」會取消目前人工標籤，舊版本仍在歷史。
3. 儲存成功才更新標籤、統計、篩選及下載版本；未儲存修改會有提示。可按主題、未分類、待主題覆核或人工已確認篩選。有效標籤可能仍是自動建議或人工未確定，頁面清楚區分狀態。每條可有多個主題，計數會重疊，不代表獨立跑手數。

主題修正保存於同一私人覆核 SQLite 的 `topic_decisions`，每次修改另存 `topic_events`；重新開啟仍保留。主題與原文身份及摘要綁定，並以項目版本、原文摘要及整份覆核版本防止過期視窗覆蓋新結果。原文、來源、保留／排除、賽事與年份修正不受主題儲存影響。相同原文改賽事／年份仍保留主題；排除後隱藏但不刪除歷史；新證據快照不自動繼承舊主題。

已確認 JSON 包括原文、來源、自動標籤及命中依據、人工有效標籤、狀態、規則版本、備註與歷史。CSV 包括自動／有效標籤、狀態、來源、版本、備註及命中依據；完整歷史見 JSON。匯出仍是整份快照，不受主題篩選影響。主題修改亦會更新 `review_fingerprint`，過期下載連結會要求重新載入。所有分類都只作私人整理，沒有情緒分析、分數或公開發布。

## 按賽事、年份及主題整理留言摘要（不評分）

在手動匯入批次按「留言摘要」，或由已確認資料集按「查看賽事／年份／主題摘要」。這是同一份清理／覆核快照的私人摘要；可篩選賽事、年份、主題、摘要狀態及搜尋摘要／原文。

- `hk-summary-extract-v1` 只對資料齊全、沒有身份衝突的人工保留項目產生重點。使用人工修正後的賽事／年份及目前有效主題，沒有主題的項目放在「未分類」。主題未確定或仍屬自動建議時，會保留明確狀態，不代為確認。
- 每項每個主題有一個獨立重點，摘錄該主題命中詞所在句；人工新增但沒有命中詞的主題取原文首句。長句最多摘錄 180 個 Unicode 字元並標為節錄，完整原文一直可見。不同留言不合寫成一句、不推算大多數／共識，摘錄保持逐字原文，不判斷好壞；節錄仍須連同完整原文核對上下文。主帖另標，不當作留言或獨立跑手。
- 每個重點都附完整原文、來源連結（如有）、作者或未知標記、主帖／留言類型及原始覆核追溯。只有主帖連結或手動未驗證來源時仍會明示；缺連結不補造。可能重複的不同來源身份會保留提醒。一條留言可出現在多個主題，重點數不等於獨立跑手或全部平台留言數。

### 人工修正摘要

1. 在「修正摘要重點」改文字，選「已人工確認摘要」或「未確定，留待判斷」，可填修正備註後儲存。兩種狀態均須有文字，最多 2000 字；人工修正文句仍需你核對是否忠於原文，系統不聲稱自動驗證語意。
2. 「未覆核／還原自動摘錄」會還原當前原文摘錄；「排除此摘要重點」只隱藏該主題下的重點，不排除原留言，也不影響其他主題的重點。可在摘要狀態篩選選「已排除重點」重新編輯。歷史保留每次文字、狀態、備註及當時分組與完整證據。
3. 只有收到「已儲存摘要第 N 版」才完成保存。未儲存修改有提示；重新開啟會還原已保存修正。摘要確認不會替代主題確認、留言保留覆核或公開內容批准。

修正保存於私人覆核 SQLite 的 `summary_decisions`，歷史另存 `summary_events`，與目前決定一起以 transaction 寫入。原文、來源、分類依據、賽事年份與摘要規則會綁定證據摘要；主題確認狀態改變時，舊人工文句會標示「依據已變」，回復自動摘錄直到再次確認。移到另一賽事／年份／主題、排除留言或證據衝突時，舊重點不留在目前摘要；既有修正及當時完整依據可在已移出分組的歷史與完整覆核 JSON 追溯。新證據快照不繼承舊摘要。單純修改留言備註不會抹去相同證據的摘要。

下載摘要 JSON 包括全部狀態、完整原文與來源、摘錄位置、人工修正與歷史，以及已移出目前分組的修正。CSV 包括全部目前重點（含已排除）、摘要／主題狀態、原文、來源、版本及備註；完整歷史請看 JSON。兩者均不受頁面篩選影響，CSV 有公式防護。下載連結綁定 `summary_fingerprint`；留言、主題或摘要更新後，舊連結回報衝突。儲存亦核對整份版本、項目版本及證據摘要，避免過期視窗覆蓋新結果。所有內容仍只作本機私人整理，沒有評分、情緒分析或公開發布。

## 同一賽事跨年份主題比較（不評分）

在手動匯入工作區按「比較同一賽事唔同年份」，或從摘要頁進入。這是並排原文證據的私人比較，不是自動趨勢判讀。

1. 先選左右各一份已保存的清理／覆核快照，再按「載入所選快照」。左右可用同一份含多屆留言的快照，亦可選分開按年份收集的兩份。舊快照不會自動合併或取代新快照；選單的「收集目標」只作辨識，實際年份仍用人工覆核修正值。
2. 選同一賽事、左邊及右邊兩個不同年份，再選全部主題或交通、寄存、水站、賽道、賽事組織等單一主題。香港內置別名按原有規則合併；自訂賽事名稱不推斷為同一場。只有一年資料時明示不足，不補造另一年留言。
3. 預設顯示有效摘要，包含自動摘錄、人工未確定及依據已變的重點，逐項清楚標示；可選只看人工確認摘要。主題是否經人工確認仍另列，不因摘要確認而代為確認主題。
4. 左右每個重點均保留原文、來源範圍、手動未驗證標記、作者、主帖／留言類型及完整追溯。「人工修正此重點／查看歷史」開啟對應快照的原有摘要重點；修改後重新載入比較便會反映，不新增另一套摘要修正。同一身份出現在兩個年份時會提示核對屆次，不當成兩位獨立跑手。

沒有可用保留資料、摘要全部已排除、以及被「只看人工確認」篩選隱藏，會分別標示。數量只描述所選快照的重點（同一留言可屬多個主題），另列留言／主帖，不代表平台全量、獨立跑手或問題發生率；不同收集量及覆核進度可能造成差異。只有一邊有資料不等於變好／變差，不推算共識、改善或退步，也沒有評分。

本次比較 JSON／CSV 只匯出所選快照、賽事、年份、主題及摘要狀態篩選。空白的一邊亦保留缺資料原因；JSON 包括每個顯示重點的完整證據及人工歷史，CSV 包括摘要與主題狀態、原文、來源、修正版本及備註，並做公式防護。完整排除項目可回各自摘要查看。兩份覆核以同一 SQLite 讀取 transaction 取得，`comparison_fingerprint` 綁定左右摘要版本及比較選擇；任何相關覆核／摘要更新後，舊下載連結會要求重新載入。

手動工作區只列出同一工作區內已準備的私人快照；獨立 `review:threads` 比較只可使用目前開啟的那份快照。原文及摘要在比較頁只作讀取，另可儲存下述人工比較備註；摘要修正仍透過原有覆核頁完成，不公開發布。

### 逐個主題的人工比較備註

每個主題的左右原文下方都有「人工比較備註」。你可以分開填「留言差異」及「待核實事項」，每欄最多 2000 字；按「儲存比較備註」並收到「已儲存備註第 N 版」才完成。系統不自動填寫差異結論，也不將待核實事項當成已驗證事實。兩欄清空再儲存可清空目前文字，舊版本仍保留。

備註綁定左右快照的方向、同一賽事、兩個年份、該主題及「有效摘要／只看人工確認摘要」篩選。單一主題及全部主題頁會顯示同一份該主題備註；換方向、快照、年份或摘要狀態篩選時不會靜默沿用。原文及來源、摘要修正、主題與保留／排除決定不受備註儲存影響。

備註保存於私人覆核 SQLite 的 `comparison_notes`，每次修改另存 `comparison_note_events`，目前版本與歷史一起以 transaction 寫入。「比較備註修改歷史及當時依據」保留每次兩欄文字、儲存時間、版本及當時左右完整重點、原文與來源。重新開啟仍保留；未儲存修改有提示。過期視窗保存會檢查整份比較版本、備註版本及證據摘要，避免覆蓋新結果。

之後若留言、主題或摘要改動，備註會保留但標示「比較依據已變，請重新核對」。就算該主題兩邊留言都已排除，原有賽事／年份選擇、舊備註及歷史證據仍可查看；目前欄位不會顯示舊留言為有效資料。重新檢查後再次儲存會綁定最新依據，歷史繼續保留。

比較 JSON 包括各主題備註、目前是否需重新核對、修改歷史及當時依據；CSV 附留言差異、待核實事項、備註狀態及版本，完整歷史見 JSON。備註更新亦會改變比較下載版本，過期連結要求重新載入。這只是私人研究備註，不代表公開內容批准、情緒分析、賽事評分或核實結論。

## 待核實事項追蹤（不評分）

在跨年份比較每個主題的已保存人工備註旁按「建立／查看這個主題的核實事項」。尚未保存備註時，先儲存比較備註，再建立追蹤。工作區主頁亦可開啟「待核實事項追蹤」，查看目前工作區所有事項。

- 每個備註可以建立多項獨立事項；原備註的「待核實事項」只預填到新增表格，按儲存才真正建立，不會自動分拆、完成或推斷核實結果。
- 狀態包括待處理、核實中、人工記錄已核實、無法確認。每項有事項文字（最多 2000 字）、結果／處理紀錄（最多 4000 字）、補充來源（每行一個 HTTPS 連結，最多 5 個）及核實／處理日期。
- 「已核實」必須填結果、有效日期及至少一個補充來源；「無法確認」須填原因及日期。來源不會自動開啟、抓取或驗證，完成狀態只代表你的人工記錄，不代表原留言、整場賽事或公開內容已獲核實／批准。可重新改為核實中或待處理，舊版本保留。
- 每項連回原比較的賽事、兩個年份、主題與快照，亦可展開相關原文及來源。只有主帖來源、作者未知或手動未經 API 驗證的標記繼續保留。修改歷史另存每次文字、狀態、結果、補充來源、日期及當時完整比較依據。

同一私人覆核 SQLite 的 `verification_tasks` 保存目前追蹤，`verification_events` 保存每次修改；兩者以 transaction 一起提交。重新開啟後保留，未儲存修改有提示；過期事項版本或比較備註／證據版本會阻止覆蓋。事項不能移接到另一份備註。手動工作區只可讀寫自己的已準備快照；獨立覆核工具只可處理目前開啟快照的追蹤。

上游比較備註修訂或原文／摘要依據改變後，即使原狀態是已核實，亦會列為「依據已變，需重新核對」，不計入目前已核實數。歷史結果不刪除；重新核對後儲存會綁定最新版本。若比較備註本身已過期，須先返回比較核對並儲存備註，才可再次記錄已核實；系統不會代為確認。

追蹤頁可按狀態或「需重新核對」篩選。下載 JSON／CSV 包含目前工作區或所選備註的範圍與狀態篩選；統計顯示該範圍總數，狀態數不包括需重查項目。JSON 包括完整修改歷史及原文依據；CSV 包括狀態、結果、補充來源、日期、版本及目前比較原文證據，並做公式防護。每個下載是當時狀態，不會自動更新。所有追蹤仍只存本機，不發訊息、不公開發布，沒有評分或自動事實判斷。

## 驗證

```sh
npm run test:threads
npm run test:threads:http
```

使用假 API 回應及臨時 SQLite，覆蓋多語搜尋、分頁、重複、父子回覆、磁碟重開續跑、Ctrl+C、中途 transaction rollback、錯誤／限流、token 洩漏防護、缺漏資料、私人路徑和 CLI。CI 會同時執行網站測試與 collector 測試。測試沒有抓取任何真實留言，也不會產生賽事分數。
